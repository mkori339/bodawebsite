BodaRequest System Documentation
================================

1. System Name
--------------

BodaRequest


2. System Purpose
-----------------

BodaRequest is a boda boda ride-request and operations management system.
Its purpose is to connect three main groups in one platform:

- Customers who need rides
- Riders who provide the transport service
- Admins who monitor trips, payments, and rider performance

The system is designed as a prototype that demonstrates the full business
process from ride request up to trip completion and admin tracking.


3. What The System Does
-----------------------

The system allows:

- Customers to register and log in
- Customers to enter pickup and destination details
- Customers to receive an estimated trip cost before confirming
- Customers to create a ride request
- Customers to complete a demo payment
- Riders to view paid ride requests
- Riders to confirm, start, and complete trips
- Admins to track daily trips
- Admins to monitor payments
- Admins to review rider activity and performance

This system is not yet connected to a real payment gateway. Payment is
currently demonstrated using a simulated payment flow.

5. Core Business Flow
---------------------

The main business flow of the system is:

1. Customer creates an account or logs in
2. Customer fills ride request details
3. System calculates and displays estimated cost
4. Customer submits the trip request
5. Trip is created with status: pending_payment
6. Customer completes demo payment
7. Trip status changes to: waiting_rider
8. Riders can now see the request
9. A rider accepts the request
10. Trip status changes to: rider_assigned
11. Rider starts the trip
12. Trip status changes to: in_progress
13. Rider completes the trip
14. Trip status changes to: completed
15. Admin dashboard reflects trips, payments, and rider updates

7. Ride Status Lifecycle
------------------------

The ride lifecycle in the current system uses these states:

- pending_payment
  Trip is created but payment is not completed yet.

- waiting_rider
  Payment is completed and the ride is now available to riders.

- rider_assigned
  A rider has accepted the trip.

- in_progress
  The rider has started the trip.

- completed
  The trip has finished successfully.

- cancelled
  Reserved for future cancellation logic.


8. Fare Calculation Logic
-------------------------

The system calculates trip cost using a simple prototype pricing model:

- Base fare
- Distance charge per kilometer
- Extra passenger charge
- Helmet support surcharge if selected
- Service fee
- Priority multiplier

Priority types in the system:

- standard
- express
- scheduled

This pricing logic is suitable for demonstration and can later be replaced
with real map-based or GPS-based calculations.


9. Payment Logic
----------------

The system currently uses demo payment logic.

Current behavior:

- Customer creates a ride
- Customer clicks pay
- System marks the payment as successful
- System stores a demo transaction reference
- Ride becomes visible to riders

This allows the business workflow to be tested before integrating real
mobile money, card, or wallet payments.


10. System Architecture
-----------------------

The project uses a 3-layer architecture:

1. Frontend
2. Backend API
3. Database

10.1 Frontend Layer

Purpose:

- Displays the landing page
- Handles user interaction
- Shows dashboards for customer, rider, and admin
- Sends requests to the backend API

Main frontend responsibilities:

- Authentication forms
- Ride request form
- Fare estimation interface
- Customer trip tracking
- Rider trip board
- Admin dashboard and monitoring views
- Theme switching between light and dark mode

10.2 Backend Layer

Purpose:

- Processes business logic
- Handles authentication
- Calculates quotes
- Stores and retrieves trip data
- Updates ride status
- Records demo payments
- Provides admin reporting data

Main backend responsibilities:

- Register and login users
- Verify JWT tokens
- Restrict access by role
- Create rides
- Calculate ride cost
- Accept payment requests
- Assign rides to riders
- Update trip progress
- Return admin metrics

10.3 Database Layer

Purpose:

- Stores users
- Stores rider profiles
- Stores ride requests
- Stores payment records

13. Security And Access Control
-------------------------------

The system includes:

- Password hashing using bcryptjs
- JWT-based authentication
- Protected API routes
- Role-based access control

Role access behavior:

- Customers can create and pay for their own rides
- Riders can only access rider trip actions
- Admins can only access admin reporting endpoints

17. System Limitations In Current Version
-----------------------------------------

This version is a prototype. Current limitations include:

- No real payment gateway
- No real-time socket updates
- No live map tracking
- No OTP or SMS notification integration
- No trip cancellation workflow yet
- Admin registration is open in demo mode for testing

19. Summary
-----------

BodaRequest is a full-stack prototype for managing boda boda ride requests.
It supports customers, riders, and admins in a single workflow.

The system is built with:

- React frontend
- Node.js and Express backend
- MySQL database

Its main purpose is to demonstrate how a ride request is created, priced,
paid for, assigned to a rider, completed, and tracked by administrators.
